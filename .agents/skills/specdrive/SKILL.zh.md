# specdrive

把用户已授权的产品开发变成可追溯的过程：

**写规格 → 审核 → 实施 → 验证与修复 → 完成后归档。**

OpenSpec 负责产物骨架、依赖顺序、任务追踪、校验和归档。本 skill 负责组织
Agent；配套本地运行器负责执行配置好的检查并记录证据，不是自主模型服务，
也不是定时调度器。

## 工作约定

- 在用户已确定的范围内自主推进。独立 AI 审核检查工程质量，不能代替产品、
  账号、付费和发布授权。用户要求逐步确认时照做，不额外增加确认门槛。
- 阅读项目规则，保留已有工作。依据上下文确认项目目录，避免误在个人主目录
  初始化 OpenSpec。
- 缺工具、缺独立审核、证据过期或场景没有实际运行，都属于未完成。
  任务打勾或编译成功本身不能证明交付完成。
- 不承诺强制限制模型 token 或费用：运行器限制的是命令尝试次数和执行时间。
  本次会话结束后继续运行，需要另外配置执行服务，或由用户恢复任务。

## 1. 写规格与审核

阅读 [OpenSpec 与宿主适配流程](references/workflow.md)。先检查已安装 CLI 的
版本和帮助，使用当前宿主真实提供的能力，不编造工具名或模型 ID。
遵循当前 schema 的依赖顺序，通常为 proposal → specs/design → tasks。

写明可验收场景、不做的内容和验证计划。每个必需场景对应实际检查或可定位的
外部证据。需要时包含异常和持久化场景，不能只验证首次顺利运行。

实现之前，让独立审核者检查产物及验收覆盖。记录被审核的版本或文件哈希、
发现的问题和结论。最多进行 **两轮审核与修订**；同一问题连续两轮未解决时
提前停止。独立审核不可用时记录阻塞，可以继续有用的准备工作，但不能假装
已经过关。审核不替代用户明确保留的产品决策。

## 2. 按有界工作流实施

读取 OpenSpec 的 apply 指令及上下文文件。只有能提高进展时，才把独立模块
或功能交给多个 Agent。先约定职责和公共接口；共享工程配置和任务打勾由一个
集成人员负责。需要隔离时用 worktree，不追求一文件一 Agent 或最大并发。
告知每位执行者：其他人也在修改项目，不要撤销他人的修改。

让每个里程碑保持可运行。任务验收条件有证据才打勾。设计变化同步到相关产物，
重大范围或架构变化重新审核。普通实现问题在已有授权内直接修复。

## 3. 验证、修复与恢复

配置或使用运行器前阅读 [运行器约定](references/runtime.md)。配置必需的环境
检查和真实行为断言，声明影响每项检查的输入，让源代码或测试变化使旧结果失效。
原生 iOS 项目还要阅读 [iOS 验证配置](references/ios.md)。

运行器记录检查输出、尝试次数、超时和当前输入哈希。Agent 在两次调用之间修复，
运行器本身不修改代码。同一失败需求最多修复三次，连续两次没有实质进展就停。
运行器还会独立限制命令执行。不能为了绕过限制或得到全绿而重置状态、弱化必需检查。

恢复任务前读取 OpenSpec 任务状态、运行器状态、工作区和上次审核。相关变化后
重跑受影响检查并更新审核。最终独立审核要对照场景查看实现和证据，不能直接接受
实施者的总结。

## 4. 完成或报告未完成事项

只有必需任务、场景、当前运行器检查、外部证据及最终审核全部通过，才能通过
OpenSpec 归档。`gate` 只检查运行器证据，不授予归档权限、不判断产品范围，
也不认证审核者身份。

仍有阻塞就保留活动变更。报告已实现内容、实际运行了什么、失败或未能运行的部分、
状态保存路径及明确的下一步。区分有用的阶段性成果和完整产品交付。
